# ADR-038: The Decision → Action bridge — a real DecisionActionResolver and ActionExecutor

## Status
Accepted.

## Context
Phase 6 (ADR-031/032) gave the system a real, explainable `IntelligenceDecision` — a closed 16-action taxonomy, every row carrying its own reason/evidence/cost/risk/confidence — but nothing turned an *approved* Decision into a real, dispatched execution. `docs/architecture/risks.md` R-37 named this explicitly: "An approved Decision is not automatically executed into a real dispatched Action." Phase 7's brief requires closing this gap without inventing a second decision taxonomy, a second workflow engine, or a second permission system.

## Decision
1. **`DecisionActionResolver`** (`lib/intelligence/action-plan.ts`, pure): `resolveActionPlan(decision)` maps the Decision's own `action` field onto a real `ActionExecutionPolicy` via a TypeScript-exhaustive lookup table — `"workflow"` for the six actions the real content-generation pipeline can execute (CREATE_PAGE, UPDATE_PAGE, REFRESH_CONTENT, CREATE_HUB, CREATE_COMPARISON, CREATE_FAQ), `"synchronous"` for two real, fast, non-workflow operations (ADD_INTERNAL_LINKS, INVESTIGATE_ENTITY), `"noop"` for MONITOR/DO_NOTHING, `"blocked"` for the six actions with no real execution path in this codebase yet. Never invents an execution path where none exists — an unsupported action is `status: "unsupported"` with a real, named reason, never a guess.
2. **`PolicyEngine`** (`lib/intelligence/policy-engine.ts`, pure-ish): the real, backend-owned gate the brief demands ("the agent must NEVER decide whether it is allowed to execute itself") — decision still approved and not expired, every required capability actually held by the recommended agent (reusing `lib/workflow/permissions.ts`'s existing framework, two new real capabilities added — `write_internal_links`, `run_research` — never a parallel permission system), and the plan's own estimated cost within the project's real, resolved budget.
3. **`ActionExecutor`** (`lib/intelligence/action-executor.ts`): `executeDecision()` is the fast, HTTP-safe entry point — resolves the plan, evaluates policy, creates a real `intelligence_actions` row (`queued` or `blocked`), never executes anything inline. `processActionQueue()` is the real drain tick, claiming via a genuine transactional `FOR UPDATE SKIP LOCKED` (the status flip happens inside the same transaction as the claim — a bare pre-transaction `SELECT ... FOR UPDATE` releases its lock before any later `UPDATE`, which would not be a real concurrency guard) and dispatching a real `WorkflowRun` (reusing `workflowEngine.start()`'s own idempotency) or a real synchronous operation to completion.
4. **Real, DB-enforced idempotency** (`migrations/0011`): a partial unique index on `intelligence_actions(decision_id)` for active statuses (`queued`/`running`/`succeeded`/`blocked`) — the same real guard `agent_runs`' own `idempotency_key` unique index already provides at the workflow layer, applied here at the Decision→Action layer. Concurrent or duplicate `/execute` calls race on this constraint and all resolve to the same real row (verified: 3 racing calls in the same test produce exactly 1 active action).
5. **A new, real `'blocked'` status**, distinct from `'failed'`: a categorical "never even attempted" outcome (unsupported action, missing capability, stale decision, budget exceeded, or a real Information Gain V2 rejection surfaced through the finalize hook — ADR-039) — never conflated with a genuine runtime error.
6. A genuinely new, Decision-driven `Opportunity` (needed when CREATE_PAGE/CREATE_HUB/CREATE_COMPARISON/CREATE_FAQ has no existing page to target) is scored with the **exact same real formula** `lib/opportunity/discovery.ts`'s batch scan already uses (`computeInformationGain`, `computeFinalScore`, `BUSINESS_VALUE_BY_TYPE` — now exported, never forked into a second copy), provenance-tracked via a new `"decision_execution"` `WorkflowPipeline` value that mirrors `trend_analysis`'s existing real-but-synchronous-provenance-run pattern (`lib/intelligence/trend-opportunity.ts`).

## Consequences
- Positive: the platform can now genuinely take an approved Decision from a real Signal all the way to a real dispatched WorkflowRun (or a real synchronous action, or an honest block) — the central, most-named gap this phase closes.
- Positive: no new taxonomy, no new workflow engine, no new permission system — every new piece is a real mapping onto, or a real extension of, what already existed.
- Negative, stated honestly: six of sixteen real action types remain `"blocked"` — no real execution path exists in this codebase yet for MERGE_PAGES, REDIRECT_PAGE, CREATE_DATASET, CREATE_CALCULATOR, EXPAND_MARKET, EXPAND_ROLE. Extending coverage means building each one a real function, not flipping a flag.
- Negative: the drain tick's dispatch (starting a workflow, running Deep Research) is not itself retried automatically on transient failure — a human/operator uses the real `POST /actions/:id/retry` endpoint, which creates a fresh, linked attempt rather than mutating the terminal row.
