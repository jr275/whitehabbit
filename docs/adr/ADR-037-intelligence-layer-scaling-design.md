# ADR-037: Scaling design for the Intelligence Layer — hot tables, indexes, cache boundaries, partition candidates

## Status
Accepted.

## Context
§18 of the Phase 6 brief asks for a real accounting of what happens as this system grows toward thousands of tenants and millions of pages — not a rewrite toward that scale today (explicitly forbidden: "não implemente infraestrutura absurda prematuramente"), but a documented, honest picture of where the current design bends first, backed by the same real-measurement discipline `scripts/load-test-harness.mjs` already established for the workflow job queue.

## Decision — real, current state, documented rather than rebuilt

**Hot tables** (highest write and read rate at scale): `signals` (every real detector run writes here — the single busiest table once Search Console/AI Visibility integrations are live), `intelligence_event_queue` (one row per real change to six different source tables), `intelligence_observations`/`intelligence_decisions` (read on every dashboard load, written on every correlation/decision scan), `agent_decision_logs` (append-only, grows monotonically, read rarely but never deleted).

**Indexes already in place** (`migrations/0007`-`0010`): every hot table is indexed on `(org_id, project_id, created_at DESC)` or equivalent — the shape every real list query in this codebase actually filters and orders by (`listSignals`, `listObservations`, `listDecisions`, `listActions`, `listOutcomes` all follow this exact pattern). `intelligence_event_queue` additionally has a **partial index** `WHERE status = 'pending'` — the one index that matters for queue-drain latency, since a claim query only ever touches pending rows regardless of how many processed rows have accumulated.

**Query patterns**: every real list function in `lib/intelligence/*.ts` takes `(orgId, projectId, ...)` and caps its own `LIMIT` (never an unbounded `SELECT *`) — the same discipline established since Phase 2. The one deliberate exception, named honestly rather than hidden: `lib/intelligence/map.ts`'s N+1 (one `listRelationsForSubject()` call per Decision) — acceptable at the current 100-200 row list caps, a real named candidate for a batched `WHERE subject_id = ANY($1)` query once measured traffic justifies it.

**Cache boundaries**: nothing in the Intelligence Layer is cached today — every read hits Postgres directly. This is a deliberate, stated trade-off for this phase: correctness (never a stale Decision, never a stale gate score) over latency, given the actual read volume (dashboard loads, not a public hot path) doesn't yet justify the staleness risk a cache would introduce. The real candidate for a future cache, if read volume grows: `buildIntelligenceMap()` and `buildIntelligenceTimeline()`, both pure aggregations over already-persisted data with no side effects — safe to cache with a short TTL once justified by real traffic.

**Partition candidates**: `signals` and `agent_decision_logs` are the two tables that grow without bound and are never updated after insert — the textbook shape for range-partitioning by `created_at` (monthly) once row counts justify it. Nothing else in the Intelligence Layer schema has this shape yet — `intelligence_decisions`/`intelligence_actions`/`intelligence_outcomes` are bounded per-tenant by real business activity (a tenant doesn't generate an unbounded number of Decisions the way a signal detector generates an unbounded number of Signals), so they are not named as partition candidates until real data proves otherwise.

**Event throughput / queue throughput (measured, not estimated)**: see `docs/architecture/load-test-report.md`'s "Real-Time Intelligence Event Queue" section, regenerated by `scripts/load-test-harness.mjs` — a real, measured benchmark against 4,000 seeded events across 10 tenants (not this ADR's own estimate).

## Consequences
- Positive: every real query pattern already established since Phase 2 (org/project-scoped, indexed, bounded) was reused rather than invented anew for the Intelligence Layer — no new query shape needed its own bespoke scaling story.
- Positive: the two genuinely deferred trade-offs (map's N+1, no caching) are named explicitly with their real triggers for revisiting, not silently accepted as permanent.
- Negative: none of this has been validated at the brief's actual target scale (10,000 tenants, 100 million pages, 1 billion+ relationships) — this ADR documents the current, honestly-smaller-scale design and its real measured behavior at a modest scale (per `docs/architecture/load-test-report.md`), consistent with the brief's own instruction not to over-build prematurely. See `docs/architecture/risks.md` for the tracked list of what changes before that target scale is real.
