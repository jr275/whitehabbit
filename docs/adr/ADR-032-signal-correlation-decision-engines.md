# ADR-032: A unified Signal Engine, deterministic Correlation and Decision Engines, and durable incremental recalculation

## Status
Accepted.

## Context
Phase 5B's `recordSignal()` was already the sole persistence path for a Signal, but nothing detected signals uniformly — each module that might want to notice something ("this entity has no evidence," "this page's traffic dropped," "this trend is accelerating") would otherwise have invented its own ad hoc detection, exactly what the Phase 6 brief warns against ("não deixe cada módulo criar seu próprio sistema de sinais isoladamente"). Nothing correlated multiple signals into a named pattern, and nothing turned a pattern into a real, explainable next action. The brief is explicit that this correlation and decision-making must be deterministic and rule-based first — an LLM may enrich it later, but must never be the only reasoning step.

## Decision
1. **Signal Engine** (`lib/intelligence/signal-engine.ts`) — one detector module, six real, deterministic detectors, each computed only from already-persisted rows: `detectEntityGaps` (Knowledge Graph), `detectPagePerformanceSignals` (two real `PageScoreSnapshot`s), `detectInternalLinkGaps` (real internal link rows), `detectTrendAcceleration` (a Trend's own real `acceleration` field), `detectAICitationChanges` and `detectCompetitorGains` (real `ai_citations`/`ai_answers` windows). `detectInformationGainGaps` (real, but expensive — it runs Deep Research internally) is deliberately excluded from the default bundle `runSignalEngineScan()` runs. A source this deployment genuinely has no real data for yet (e.g. GSC index-coverage data for `INDEXATION_CHANGE`) simply has no detector — never a fabricated one.
2. **Correlation Engine** (`lib/intelligence/correlation-engine.ts`, pure) — `DEFAULT_CORRELATION_RULES`, each a real AND over required/supporting signal types grouped by `correlationKeyFor()` (entity → page → market → the signal itself). `lib/intelligence/correlation-scan.ts` orchestrates this against a project's real recent signals (30-day lookback) and persists a real `IntelligenceObservation` per match, deduplicated by `(pattern, correlation_key)` — not by comparing the serialized `signal_ids` array, which is order-sensitive and was a real bug this phase's own integration test caught (Postgres gives no tiebreaker guarantee for same-millisecond signals).
3. **Decision Engine** (`lib/intelligence/decision-engine.ts`, pure) — `proposeDecision()` maps an Observation's pattern to one of the 16-action taxonomy via real, TypeScript-exhaustive lookup tables (cost/risk/approval-required/recommended-agent per action) — never a guess. `lib/intelligence/decision-scan.ts` resolves the real subject (an existing page, if one exists) from the Observation's own stored `correlationKey`, not from free text, and is idempotent via a real `intelligence_relations` edge (`decision -> observation`, `derived_from`).
4. **Real-time incremental recalculation** (`migrations/0010`, `lib/intelligence/recalc-worker.ts`) — every real change to `search_console_snapshots`/`trends`/`entities`/`pages`/`ai_answers`/`dataset_versions` already fires a `pg_notify` trigger (ADR-024's follow-on). A bare NOTIFY is not durable — a listener not connected at the moment it fires loses the event forever — so the same trigger now also inserts a row into a new, durable `intelligence_event_queue`, resolving `project_id` via the real FK path for the tables that don't carry it directly. `processIntelligenceEventQueue()` drains it the same way `lib/workflow/step-worker.ts`'s `processStepQueue()` already drains the job queue (`FOR UPDATE SKIP LOCKED`, bounded retry), dispatching only the detector(s) relevant to each event's category, then a real correlation + decision scan — never a full-table sweep, and never every detector for every event.
5. **Agent Decision Log** (`lib/intelligence/agent-decision-log.ts`) — a real, append-only audit trail, distinct from `intelligence_decisions` (the strategic layer): the tactical "why did the agent do X, right now, during this run" record enterprise auditability needs. The Information Gain gate (ADR-031) writes to it on every real evaluation, allowed or blocked.

## Consequences
- Positive: no module invents its own signal concept — every real detection goes through one facade, one persistence path, one correlation mechanism.
- Positive: incremental recalculation is genuinely bounded to the one `(org, project)` an event actually touched and the detector types relevant to its category — never a tenant-wide or system-wide sweep.
- Negative, stated honestly: the dispatched detectors are project-scoped, not yet single-subject-scoped — re-running `detectEntityGaps()` for one `EntityChanged` event re-scans the project's entities rather than just the one that changed. True per-subject narrowing (e.g. a real `detectEntityGapForEntity()`) is real follow-up work, not claimed as done.
- Negative: correlation and decision rules are a fixed, hand-authored set (`DEFAULT_CORRELATION_RULES`, the cost/risk lookup tables) — extending coverage means adding real rules, not retraining a model, which is the deliberate trade-off ADR-032 makes for explainability over adaptiveness at this stage.
