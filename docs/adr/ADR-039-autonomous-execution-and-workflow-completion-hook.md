# ADR-039: Autonomous execution under explicit policy, and observing workflow completion without a poll

## Status
Accepted.

## Context
Two real design problems Phase 7 had to solve to make execution genuinely autonomous rather than fire-and-forget: (1) execution must remain backend-owned — an agent must never decide its own permission to run, matching the existing autonomy discipline (`lib/workflow/autonomy.ts`, ADR-020) — while not duplicating that mechanism a second time; (2) a dispatched, workflow-backed Action needs to know, reliably, when its underlying `WorkflowRun` finishes (succeeded/failed/cancelled) so its own status can be updated — without polling, and without every one of the several real call sites that can finalize a workflow (an API route's catch block, the queue-driven step worker's `applyOutcome()`, a dead-lettered job) having to remember to notify the Intelligence Layer.

## Decision
1. **Autonomy stays layered, not duplicated.** `lib/workflow/autonomy.ts`'s `evaluatePublishAutonomy()` (LEVEL_0–4) is unchanged and still the one real gate for the specific, highest-risk moment — publishing — inside the content-generation pipeline's `decide_publish` step. The new `PolicyEngine` (ADR-038) is a distinct, earlier gate: whether an *already human-approved* Decision's plan can be dispatched at all right now (capability, freshness, budget) — not a second opinion on whether the strategy itself was sound, which the human approval already settled. A Decision's own `requiredApproval`/approval-by-a-real-actor (`decideOnDecision()`, unchanged since Phase 6) remains the one real human checkpoint for "should this happen."
2. **A real completion hook, not a poll.** `lib/workflow/engine.ts#finalizeWorkflow()` — the one real choke point every workflow's terminal transition passes through regardless of trigger — now calls `onWorkflowFinalized()` (`lib/intelligence/action-executor.ts`) after the run's own status transition succeeds. Implemented via a **dynamic** `import()`, not a static one: `action-executor.ts` calls back into `lib/workflow/engine.ts` (`workflowEngine.start`, `runStep`, `finalizeWorkflow`), so a static import in the other direction would be circular. A dynamic import also sidesteps a real module-resolution hazard the first version of this hit — `lib/api-error.ts` transitively imports `next/server` and (through `lib/session.ts`) the real, unmocked `next-auth` stack, which broke module resolution in any Vitest test context that reaches a workflow's terminal state without itself mocking `@/lib/auth`. Any error from the hook is logged and swallowed, never allowed to break the workflow's own authoritative status transition.
3. **A real, string-matched signal for the one case that needs to be distinguished specially.** §9 of the brief requires a real Information Gain V2 rejection to become a categorical `BLOCKED` outcome, not a generic failure. The hook pattern-matches `errorReason` against `evaluateInformationGainGate()`'s own real, stable message prefix (`/^Information Gain \d+/`) — the only signal available without a larger structured-error-code refactor across the workflow engine. Documented as a real, load-bearing string match, not hidden.

## Consequences
- Positive: execution is genuinely autonomous under explicit, backend-owned policy — never the agent's own call — while adding no second copy of the autonomy mechanism.
- Positive: every real workflow-completion path (API route, queue worker, dead-letter handler) gets the hook for free, with zero risk of a future call site forgetting to wire it in.
- Negative: the dynamic-import + string-match pattern is a real, deliberate trade-off for a generic infrastructure module (workflow engine) needing to notify a domain layer (Intelligence) without a hard dependency — a cleaner long-term shape (a real event-bus/hook-registry primitive) is legitimate future work if more domain layers need the same kind of notification.
- Negative: the string-match is coupled to `evaluateInformationGainGate()`'s exact message format — a future rewording of that message would silently stop being recognized as a `BLOCKED` case (falling back to `'failed'`, still correct-ish but less precise) unless the pattern is updated alongside it.
