# Architectural Risks & Missing Requirements

Numbered so ADRs and the roadmap can reference them (`R-n`). Each has a
trigger condition, not just a description — "known and deferred" is only
honest if the deferral condition is written down.

| ID | Risk / missing requirement | Where named | Trigger to address |
|---|---|---|---|
| R-1 | Tenant isolation is application-layer only; no PostgreSQL RLS | ADR-001 | Before onboarding tenants whose contractual/compliance requirements demand defense-in-depth beyond app-layer checks; or opportunistically once the Phase-2 schema (this revision) stabilizes. |
| R-2 | Only two membership roles (owner/member); brief's full role set (OWNER/ADMIN/EDITOR/ANALYST/AGENT_OPERATOR/VIEWER) not implemented | ADR-001 | First feature that needs to distinguish, e.g., who can approve an Opportunity vs. who can only view one. |
| R-3 | ~~No automated "Tenant A must never access Tenant B" test suite~~ — **resolved**: `tests/integration/tenant-isolation.test.ts` covers entities, opportunities, pages, and agent runs at both the repository and real API-route layers. | ADR-001 | Extend as new resource types are added (e.g. websites, page briefs) — not yet covered explicitly. |
| R-4 | ~~No real Entity Resolution~~ — **partially resolved**: `lib/knowledge/resolution.ts` implements real, configurable-threshold auto-merge/review/distinct decisions, used by the crawl-based extraction path (`resolveOrCreateEntity`). The older `skill_seo_opportunity` ingestion path still uses exact-match-only `upsertEntityByName`. | ADR-002, ADR-009 | Migrate `lib/opportunity/ingest.ts` to `resolveOrCreateEntity` too, once that path's entity volume justifies it. |
| R-5 | Autonomy levels (§25, LEVEL 0–4) not configurable per tenant; every write/publish/financial/external-comm tool action requires approval unconditionally today | ADR-003 | Before any tenant needs LEVEL 2+ (AI-initiated low-risk publishing) — currently no publishing capability exists at all, so this is not yet blocking anything. |

| R-8 | No model routing (cheap vs. strong model per task) | ADR-008 | First task cheap enough to not need the default reasoning model — a candidate is entity-name dedupe in `lib/knowledge` once Phase 3's crawler produces higher entity volume. |
| R-9 | No explicit CSRF token on state-changing routes beyond NextAuth's session-cookie SameSite defaults | ADR-011 | Should be addressed alongside R-3 in priority — recommend before this revision's new mutation endpoints (`PATCH /api/opportunities/:id`) see production traffic from a UI with cross-origin exposure. |
| R-10 | No metrics/tracing backend beyond structured logs + querying Postgres directly | ADR-012 | Once execution volume makes ad-hoc Postgres queries insufficient for operational visibility, or Phase 4/6 creates a second process to correlate against. |
| R-11 | Opportunity field edits (once an edit UI exists) have no version history, only current-state + audit log of status transitions | ADR-014 | Before shipping free-text editing of an Opportunity's title/outline (not built in this revision — approve/reject only). |
| R-12 | `getOrCreateDefaultProject()` means multi-project-per-tenant is schema-ready but not yet a real onboarding flow — every org effectively has exactly one Project today | Domain model | Phase 3's real website-onboarding flow (§9) should let a tenant explicitly create/name additional Projects rather than relying on the lazy default. |
| R-13 | ~~`Project.primary_domain` is a free-text field, not a verified/enforced domain binding~~ — **resolved**: `domains`/`domain_verifications` (ADR-018) provide real DNS-verified domain binding; `resolveVerifiedDomain()` is the only function public rendering may use, and never trusts an unverified hostname. `Project.primary_domain` itself is unchanged (still descriptive text) but is no longer the security-relevant path. | ADR-018 | TLS/SSL provisioning for a verified custom domain is not implemented (see R-20) — address before routing real production traffic through a custom domain. |
| R-14 | ~~No durable workflow engine; long-running/resumable agent steps are not yet possible~~ — **resolved**: `lib/workflow/*` (ADR-017) provides checkpoint-resume, retry, budgets, and a real state machine; both existing pipelines were migrated onto it. | ADR-017 | — |
| R-15 | Monorepo/package split not done; `lib/` has no build-enforced dependency boundaries between domains | ADR-000 | Either roadmap Phase 6 (second real deployable) or `lib/` becoming unwieldy by team feedback, whichever comes first. |
| R-16 | ~~Website discovery and content generation run synchronously inside one HTTP request~~ — **fully resolved (Phase 5A, ADR-023)**: no HTTP request runs a whole pipeline, or even a whole step's worth of retries, inline anymore. Every step is dispatched as its own independent, durable, tenant-scoped, crash-recoverable job (`lib/workflow/step-worker.ts`); starting/resuming/retrying a workflow, or approving a publish, only ever enqueues the next single step and returns. Proven in `tests/integration/step-execution.test.ts`. | ADR-003, ADR-016, ADR-017, ADR-023 | — |
| R-17 | No lint tooling (ESLint/`next lint`) is configured anywhere in this repository — pre-existing, not introduced by this revision. `tsc --noEmit` and `next build` are the real, enforced quality gates today. | — | Worth adding once a team beyond one contributor is working in this codebase; low risk today given TypeScript strict mode already catches most of what lint would. |
| R-18 | Entity/Opportunity/Page quality depends heavily on real structured data (JSON-LD) existing on the crawled site; a site with none will still crawl and profile correctly but will discover few or no entities/opportunities | ADR-002, `lib/knowledge/extraction.ts` | A second extraction signal (e.g. a real NLP/LLM-based extractor for sites with no structured data) — deliberately not built now to keep extraction deterministic and evidence-first; would need its own confidence/evidence discipline to avoid regressing §9's "never fabricate" rule. |
| R-19 | The Draft step's `LLM_DEV_MODE` fixture (`lib/agent/tools/llm-providers/development.ts`) now echoes the real prompt's target intent and research claims so the pipeline is meaningfully testable without a real LLM credential — but it is still not real prose generation, so a dev-mode "ready" page's actual writing quality is not representative of a real provider's output. | `lib/content-pipeline/draft.ts` | Not a gap to close — dev mode is explicitly never reachable in production (`lib/runtime-mode.ts`'s `isDevModeAllowed()`); named here only so nobody mistakes a dev-mode "passed quality gate" result for evidence about real-provider content quality. |
| R-20 | No TLS/SSL provisioning for a tenant's verified custom domain — DNS ownership verification (ADR-018) is real, but serving HTTPS on that domain in production needs a real certificate-provisioning flow (e.g. a Vercel/Let's Encrypt-style ACME integration) that isn't built. | ADR-018 | Before routing real production traffic through a tenant's custom domain rather than the platform's own `/sites/:projectId/:slug` path. |
| R-21 | Each open `/api/v1/workflows/:id/events` SSE connection holds one dedicated Postgres `LISTEN` connection (ADR-021) for its duration — not pooled. At meaningful concurrent-viewer counts this is a real connection-budget constraint. | ADR-021 | Before relying on the live event stream at high concurrent-viewer scale — revisit as a single shared `LISTEN` connection fanning out to many HTTP responses in-process. |
| R-22 | ~~`tenant_budgets` is a real table but nothing reads it yet~~ — **resolved (Phase 5A)**: `lib/workflow/budget-policy.ts#resolveConcurrencyLimit()` reads it inside `dequeue()`'s admission loop (per distinct org per tick, cached); `resolveBudgetPolicy()` resolves a run's `BudgetPolicy` as workflow override → `project_budgets` (new table) → `DEFAULT_BUDGET`. **Not resolved**: no management UI/API to set these yet — only the resolution mechanism and the repo functions (`upsertTenantBudget`/`upsertProjectBudget`) exist. | ADR-019, ADR-022, ADR-023 | First tenant/project that needs a real override set via API/UI rather than direct SQL. |
| R-23 | Approval reviewer authorization is "any authenticated member of the tenant org" — there is no reviewer role distinct from any other org member (see also R-2's broader role gap). | ADR-020 | Before a tenant needs to restrict who may approve a publication vs. who may only draft/view one. |
| R-24 | `RouteTemplate` binding (§19, ADR-016 amendment) is classification-only: a page records which active template it matched, through a real vertical-agnostic matcher, but public URL resolution still goes through the simpler `(projectId, slug)` path rather than rendering a template's own `pattern`. | ADR-016, roadmap.md Phase 6 | Once a tenant's page volume or SEO requirements need URLs that literally follow a template's pattern (e.g. `/{city}/{propertyType}/{intent}`) rather than a flat slug. |
| R-25 | ~~pause()/cancel() cannot interrupt a synchronous orchestrator call already in flight~~ — **resolved (Phase 5A, ADR-023)**: since every step is now its own job, pause/cancel takes effect between any two steps, not just between whole-pipeline invocations — a stray step job dispatched for a paused/cancelled run is a real no-op (proven in `tests/integration/step-execution.test.ts`). **Still true**: a step itself, once started, is not interruptible mid-execution — it either finishes or the job's lease expires and it's recovered. | ADR-017, ADR-023 | Interrupting mid-step would need real cancellation tokens threaded through every step's I/O (crawl fetch, LLM call) — not pursued; a bounded step re-attempting from its own start on recovery is the accepted granularity. |
| R-26 | Completing one whole pipeline now costs 4-7 sequential step-job dispatches instead of 1 (Phase 5A's real, accepted durability trade-off — see `docs/architecture/load-test-report.md`'s before/after section and ADR-023). At the measured per-tick dequeue rate and a 5-minute cron cadence, draining a target-scale (100k page) backlog from zero would take on the order of weeks of continuous worker time alone. | ADR-023 | Before relying on the current single 5-minute-cron worker tick at target page volume — needs either a shorter cron interval (cost/plan decision) or more parallel worker capacity per tick, not new architecture. |
| R-27 | This test suite's integration/e2e tests share one real Postgres database (truncated once at suite start, not per file) and, since Phase 5A, a real global job queue — running test FILES in parallel (Vitest's default) let two files race over the same queue rows nondeterministically, a real bug this phase's own tests surfaced and fixed by setting `fileParallelism: false` in `vitest.config.ts`. | `vitest.config.ts` | Revisit if the test suite's runtime becomes a real bottleneck — would need per-file queue/DB isolation (e.g. a schema-per-file or a queue-scoping mechanism) to safely re-enable parallelism, not just flipping the flag back. |
| R-28 | Search Console's live OAuth path (`lib/intelligence/search-console/live.ts`) is real, reviewable code but genuinely untested end-to-end — no real Google service-account credential or property exists in this environment. Only the request-shape/error-handling logic is unit-tested via an injectable fetch. | ADR-025 | Before relying on the live path in production — configure real `GOOGLE_SEARCH_CONSOLE_*` credentials and verify against a real property once available. |
| R-29 | AI Visibility answers never carry a sentiment (`AIAnswer.sentiment` is always `null`) — no real second signal exists to classify it honestly. | ADR-028 | A real sentiment classifier (a second real LLM call, or a validated heuristic) with its own confidence discipline — not a keyword guess. |
| R-30 | ~~Information Gain V2 + Gate is real and callable but not wired into the actual page-generation blocking path~~ — **resolved (Phase 6D, ADR-031)**: a real `information_gain_gate` step now runs between `research` and `outline` in the real content-generation pipeline; below threshold, generation stops before any LLM call, with a real reason and a real Agent Decision Log entry. Its first real run also surfaced and fixed two real bugs (dead `sourceType` heuristic, an unreachable REJECT branch) — see ADR-031. | ADR-027, ADR-031 | — |
| R-31 | The Recommendation Engine has three real rules (refresh_page, create_data_asset, investigate_query) — the brief's fuller example list (merge_pages, build_calculator, add_entity_relationship) needs real trigger signals (a duplicate-content detector, a calculator-worthy-data detector) this revision doesn't compute yet. | ADR-030 | Each additional rule, in order of real signal availability — a real cannibalization/duplicate-content detector is the natural next one. |
| R-32 | Evidence is split across two tables (`entity_evidence` for entities, `evidence` for everything else) — no single query returns "all evidence connected to entity X" including evidence attached to opportunities about X. | ADR-029 | A real, tenant-scoped aggregation query or view, once a real product surface needs a unified evidence view. |
| R-33 | No dedicated UI exists for the Intelligence Layer (Mission Control V2, Opportunity Map V2, Intelligence Timeline, §34-37) — this phase was deliberately API-first. | roadmap.md Phase 9 | Once the underlying data model has real production usage to visualize — building the UI before real trends/signals/recommendations exist at any tenant would mean designing against fixtures, not real shapes. |
| R-34 | The trend→opportunity eligibility bar (confidence ≥ 0.6, state ∈ {emerging, rising, breaking}) is a reasonable first cut, not yet tuned against real production trend volume — no real tenant has generated trends yet to tune against. | ADR-026 | Revisit once a real tenant's Search Console data has run through the trend scan for at least a few real weeks. |
| R-35 | Query normalization's entity matching (`lib/intelligence/search-console/normalize.ts`) is real substring matching against already-known canonical entities — never NLP/ML-based. A query naming an entity the Knowledge Graph doesn't know about yet correctly gets no match, which is honest but means normalization quality is bounded by how complete the Knowledge Graph already is. | ADR-025 | A real NLP/LLM-assisted entity extraction pass over query text — would need its own confidence discipline (§40) to avoid fabricating entity matches, not built now to keep normalization deterministic. |
| R-36 | Signal-engine detectors dispatched by real-time incremental recalculation (Phase 6E) are project-scoped, not single-subject-scoped — an `EntityChanged` event re-scans a project's entire entity list rather than just the one entity that changed. Real, bounded (never cross-tenant, never every detector), but not the finest-grained incrementality possible. | ADR-032 | Add subject-filtered detector variants (e.g. `detectEntityGapForEntity()`) once a project's real entity/page counts make the full-project rescan measurably expensive — `docs/architecture/load-test-report.md` names this explicitly. |
| R-37 | ~~An approved `IntelligenceDecision` is not automatically executed into a real dispatched Action~~ — **resolved (Phase 7, ADR-038)**: `lib/intelligence/action-executor.ts`'s `executeDecision()`/`processActionQueue()` really, durably dispatch a real `WorkflowRun` (six real action types) or a real synchronous operation (two more), with a real `DecisionActionResolver` + `PolicyEngine` gate. | R-41 | ~~Phase 6 continued Phase 9's API-first posture — no dedicated Mission Control/Opportunity Map/Decision Center UI was built~~ — **partially resolved (Phase 7, ADR-040)**: `/mission` and `/intelligence/decisions` are real, working UI over real data. **Still true**: the Opportunity Map graph visualization (ADR-042, deliberately deferred), a rebuilt Agent Run Inspector, and a Live Agent Graph remain unbuilt. | roadmap.md Phase 10/11, ADR-040, ADR-042 | Build the Opportunity Map UI against the already-real `/intelligence/map` endpoint (ADR-042) — real backend, no further API work needed first. |
| R-42 | Six of the Decision Engine's 16 real action types (MERGE_PAGES, REDIRECT_PAGE, CREATE_DATASET, CREATE_CALCULATOR, EXPAND_MARKET, EXPAND_ROLE) have no real execution path — `resolveActionPlan()` honestly reports them `"unsupported"` and the ActionExecutor `BLOCKED`s them rather than attempting anything. | ADR-038, `lib/intelligence/action-plan.ts` | Build each one a real function as real signal justifies it — CREATE_DATASET is the closest to real (`ingestDataset()` already exists) but needs a real way to resolve which DataSource/external id a Decision should ingest, which the Decision itself doesn't carry today. |

## Missing requirements carried forward without a risk ID (explicitly out of
this revision's and near-term roadmap's scope, restated here so they are not
silently forgotten)

- Community Signal Engine (§21) — needs a real community-source integration
  first; no such integration exists.
- Deep Data Engine / DataSourceDiscoveryAgent (§20) — needs a target page
  type to know what "better than competitors" means for; sequenced after
  Phase 5/6.
- White-label / second demo vertical proof (§77, "Acme Travel") — the
  generic `entity_type` free-text design (ADR-002, domain model) already
  makes this possible without core changes; the proof itself (seeding a
  second tenant with a non-real-estate ontology) is a Phase 3+ demo task,
  not an architecture task, and should be done once there's a real second
  Project/onboarding flow to seed it through.
